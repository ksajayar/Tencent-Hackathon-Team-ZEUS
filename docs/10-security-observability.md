# 10 — Security, Logging & Error Handling

Covers brief sections 21, 22 and 23.

## 10.1 Security

Scoped honestly for a hackathon: the controls below are the ones that are cheap and matter.
Items marked `DEFERRED` are named so you can answer a judge's question, not built.

### OAuth
- Read-only scopes only. No code path in this system can send, delete, or modify anything in
  a Google account. This is a design property worth stating in the pitch.
- Single-use `state`, 10-minute expiry, bound to `user_id`.
- Exact `redirect_uri` match, registered in the Cloud Console.
- `access_type=offline` + `prompt=consent`.
- Revocation endpoint that actually calls Google's revoke, not just a local delete.

### Secrets
- Everything through Railway environment variables. Nothing in the repo, ever.
- `.env.example` with keys and empty values, committed. `.env` in `.gitignore`.
- `pydantic-settings` validates at boot — a missing secret fails the deploy, not the demo.
- Required: `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_WHATSAPP_FROM`,
  `GEMINI_API_KEY`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `DATABASE_URL`,
  `TOKEN_ENCRYPTION_KEY`, `MEDIA_SIGNING_KEY`, `ADMIN_TOKEN`, `PUBLIC_BASE_URL`.

### Encryption
- Google tokens: Fernet (AES-128-CBC + HMAC), key from `TOKEN_ENCRYPTION_KEY`, stored as `bytea`.
- In transit: TLS everywhere. Railway terminates TLS at the edge and provides the certificate.
- `DEFERRED`: key rotation, field-level encryption of message content, encrypted volume.

### Transport
- HTTPS enforced. Reject plain HTTP.
- HSTS on the OAuth routes.
- Twilio's webhook signature validation depends on the exact public URL — build it from
  `PUBLIC_BASE_URL`, not from `request.url`, because Railway's proxy reports `http` internally
  and every signature will fail if you don't.

### Input validation
- Pydantic on everything parsed. Twilio's form payload is validated into a typed model before use.
- Message body length cap (4096) before it reaches the model.
- Reject unexpected content types outright.
- **Prompt injection:** a photographed document or an email can contain instructions aimed at
  the model. Mitigations: user content goes in clearly delimited blocks, the system prompt
  states that content inside those blocks is data and never instructions, and the output guards
  (medication guard, SOS-is-regex-only) mean a successful injection still cannot produce a
  fabricated medication instruction or a false emergency. **This is the main reason the safety
  guards are structural rather than prompt-based.**

### File validation
- Size caps enforced before download, from `Content-Length`, and again after.
- MIME sniffed from magic bytes with `python-magic` — never trust `MediaContentType`.
- Allowlist: `image/jpeg`, `image/png`, `audio/ogg`, `audio/mpeg`, `audio/amr`,
  `application/pdf`, `text/vcard`. Everything else is rejected with a friendly message.
- PDFs: page-count cap (30). Never execute, never follow embedded links, never render JS.
- Filenames generated by you from the SHA-256, never taken from user input. Kills path traversal.
- `DEFERRED` — **malware scanning.** There is no AV in this system. The honest mitigation:
  files are never executed, never served back to anyone but Twilio, and are deleted after 7
  days. Production would add ClamAV or an object-storage scanner. Say this if asked rather than
  claiming protection you don't have.

### SQL injection
- SQLAlchemy parameterised queries only. No f-strings in SQL, no `text()` with interpolation.
- If a raw query is unavoidable, bound parameters only.

### Rate limiting
- Per WhatsApp sender: 20 messages/minute. Protects your Gemini quota more than your server.
- Per IP on OAuth routes: 10/minute.
- Global Gemini token bucket sized under the free-tier RPM.
- SOS is **exempt from user-facing rate limiting** beyond a 5-minute per-contact cap on
  notifications. Never rate-limit someone out of an emergency.

### Authorisation
- Every user-scoped query filters `user_id`. This is the entire tenancy model, so it must be
  right in every query. Put it on the code-review checklist.
- Internal endpoints behind `X-Admin-Token`, excluded from the OpenAPI schema.
- No JWT session layer: there is no user-facing web UI to authenticate. `DEFERRED` to whenever
  a caregiver dashboard exists — at which point JWT with short expiry and refresh rotation.

### Privacy
- Health-adjacent data about a vulnerable person. Under Singapore's PDPA, consent, purpose
  limitation, and reasonable security apply. For a demo with synthetic data this is not a legal
  exposure, but **the plan should state that a real deployment needs a consent mechanism the
  patient can meaningfully give — which is a genuinely hard problem when the user has dementia,
  and is usually solved by a legally authorised representative.** Worth one line in the pitch;
  it shows you understand the domain.
- Free-tier Gemini may retain prompts for training. Synthetic data only. Non-negotiable.

## 10.2 Logging

`structlog`, JSON to stdout, picked up by Railway's log viewer.

### What gets logged

| Level | Content |
|---|---|
| `INFO` | Message received/sent (SID, user_id, kind, language, latency), job start/finish, sync counts, OAuth grant/refresh |
| `WARNING` | Gemini 429, retry, degraded-mode fallback, window closed, low transcription confidence, medication guard rejection |
| `ERROR` | Send failure after retries, unhandled pipeline exception, DB error, token refresh `invalid_grant` |
| `CRITICAL` | Medication reminder failed to deliver, SOS notification failed |

### What never gets logged

Message bodies · transcripts · email subjects or content · OCR output · coordinates ·
tokens · API keys · patient name in free text.

Enforce with a `structlog` processor that drops a denylist of keys and truncates any string
field over 200 chars. Do not rely on developers remembering — the demo will be built fast.

### Correlation

A `request_id` per webhook, propagated to every log line in that message's lifecycle, including
across the async handoff to the worker. Without it, tracing one message through six pipeline
stages in a shared log stream is impractical.

### Audit log

Separate from application logs, in Postgres, for actions rather than events: token
issue/refresh/revoke, medication create/verify, SOS trigger and outcome, caregiver
notification, data deletion. Queryable, retained, never deleted by the cleanup job.

### Monitoring

- `/health` for Railway's health check.
- `/metrics` returning counters: inbound/outbound counts, per-pipeline latency percentiles,
  Gemini tokens and 429 rate, queue depth, failed sends, scheduler last-run timestamps.
- **Queue depth and scheduler last-run are the two numbers to watch.** Both failing silently
  is the realistic failure mode.
- `DEFERRED`: Sentry, Prometheus, uptime pinger. A `/metrics` page you check manually is
  proportionate for a demo. Add an uptime pinger the day before if you want to sleep.

## 10.3 Error handling

Universal rules:

1. **The webhook always returns 200** unless the signature is bad. Any other status makes
   Twilio retry and duplicate the message.
2. **Every external call has a timeout.** No exceptions.
3. **Every failure has a user-visible fallback in the patient's language.** Silence is the
   worst outcome — a confused user staring at an unanswered message is worse than an error.
4. **Never expose an exception to the user.** Simple sentence, logged detail.

### Per-dependency

| Failure | Detection | Handling | User sees |
|---|---|---|---|
| **OAuth: user denies consent** | callback with `error=access_denied` | Log, no retry | "No problem. You can connect your email later." |
| **OAuth: state invalid/expired** | not found or `used_at` set | Generic error page | "That link expired. Say 'connect google' for a new one." |
| **OAuth: `invalid_grant` on refresh** | 400 from token endpoint | Delete token row, flag user | "I lost access to your email. Say 'connect google' to fix it." |
| **Gmail 401** | HTTP 401 | Refresh once, retry once, then treat as above | Cached email still served |
| **Gmail 429 / quota** | HTTP 429 | Back off, skip cycle, halve poll rate for an hour | Cached data, silent |
| **Calendar 410 stale syncToken** | HTTP 410 | Drop token, full re-list | Nothing |
| **Gemini 429** | HTTP 429 | Backoff + jitter, 3 attempts, then degraded mode | "Give me a moment…" then the degraded answer |
| **Gemini timeout** | >45s | Abort, degraded mode | Templated answer from the DB |
| **Gemini malformed JSON** | Pydantic validation fails | Retry once with the error fed back, then rules-based fallback | Degraded answer |
| **Transcription empty/low confidence** | confidence <0.5 or empty | No guessing | "I couldn't hear that clearly. Could you say it again?" |
| **OCR low confidence on a medical field** | confidence <0.8 | Suppress the value entirely | "I can't read this clearly — please ask your caregiver." |
| **TTS (edge-tts) fails** | exception or empty file | Fall back to Google Cloud TTS if configured, else text-only | Text reply, no audio. Never an error. |
| **ffmpeg missing/fails** | non-zero exit | Text-only reply, `CRITICAL` log | Text reply |
| **Twilio 63016 (outside window)** | status callback | Re-route through template; indicates a gateway bug | Delayed message |
| **Twilio 63007** | status callback | On the old sandbox this meant "hasn't joined" - doesn't apply to this number (no join step). Alert operator and check the Console debugger; not independently verified against a production sender. | Nothing (they can't receive) |
| **Twilio 63005 (media rejected)** | status callback | Log MIME/size/filename, send text-only | Text reply |
| **Twilio 5xx** | HTTP 5xx | Queue, retry ×3 with backoff | Delayed message |
| **Media download fails** | HTTP error / timeout | Retry ×2 | "I couldn't open that. Could you send it again?" |
| **Postgres connection lost** | `OperationalError` | Pool retry; if sustained, fail health check so Railway restarts | Nothing during a brief blip |
| **Postgres constraint violation** | `IntegrityError` | Usually a duplicate `channel_sid` — that's idempotency working, not an error. Log at DEBUG. | Nothing |
| **Railway restart / redeploy** | process exit | In-flight in-memory queue items lost — but every message is already persisted, so a recovery pass on boot re-enqueues anything `status='received'` with no outbound reply | Slight delay |
| **Railway out of credit** | service suspended | Nothing works. Prevention only: check the balance the day before. | — |

### The boot recovery pass

On startup, re-enqueue every inbound message with `status='received'` and no corresponding
outbound reply, from the last 24 hours. This is what makes "write first, process later" safe:
a crash mid-pipeline costs a delay, never a lost message. It is about fifteen lines and it is
the difference between a robust demo and one that dies the first time Railway redeploys mid-conversation.
